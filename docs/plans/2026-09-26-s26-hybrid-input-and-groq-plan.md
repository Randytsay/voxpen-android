# Samsung S26：嘸蝦米、拼音與 Groq 語音整合開發計畫

日期：2026-09-26

狀態：Debug APK 已建置；Samsung S26 真機驗收與資料升級驗證待執行

目標裝置：使用者的 Samsung S26；實際 Android、One UI 版本於真機階段記錄。

## 1. 開發方向與成功定義

以 VoxPen Android 為產品主體，沿用 Android 鍵盤、錄音、Groq 轉錄與文字輸出；參考 MixType 的音節解析、多路切分及候選分組方法，在 Kotlin 實作混合輸入核心。

日常使用方式：在同一個鍵盤直接輸入嘸蝦米或拼音，候選列同時提供可選文字；想用說的時候按麥克風，停止後取得辨識結果，點選插入，再繼續打字。

「完美結合」以可測量行為定義：完整嘸蝦米碼不被錯誤候選擠掉、拼音不漏掉合理切分、常用詞容易選到、切換語音不遺失組字、不重複插入、不把結果送到另一個欄位。辨識率與候選品質需用使用者真實語料確認，不承諾所有輸入都能猜中。

### 第一版 P0 必須完成

- 同一字碼同時查嘸蝦米與拼音，免切換輸入模式。
- 嘸蝦米、全拼與首字母候選同列按命中精確度、詞頻和個人學習排序；碼源碰撞不再一律讓嘸蝦米完整碼壓過精確拼音詞。
- 支援連續全拼、首字母、全拼與首字母混合，如 `nihao`、`nh`、`nhao`。
- 支援合法歧義切分，例如 `xian`、`fangan`；尊重使用者輸入的分隔符。
- 單字母可查常用多字詞；有可追溯的常用度權重。
- 選取合成候選後可記住相同讀音與文字的偏好。
- 比照 MixType：詞語預設三次有效確認後加入長期個人詞庫；拼音單字三次明確選取後參與同讀音候選的偏好排序。
- 提供個人詞典介面，手動新增、搜尋、修改與刪除詞語及讀音；例如「耀文／yao wen」儲存後立即可用 `yw` 查到，不需三次學習。
- Groq 採錄音結束後送出轉錄，提供原文預覽與手動插入。
- 語音與打字共用一個文字輸出入口，管理欄位生命週期與重複回呼。
- S26 真機通過效能、相容性、升級保留資料與回退驗收。

### 後續 P1 / P2

- P1：在直接候選不足時啟用有限的首字母錯字容忍，清楚區分精確與模糊候選。
- P1：根據真機記錄調整常用詞、分段數懲罰與個人偏好權重。
- P2：任意多組嘸蝦米碼與拼音連續串接、自動辨識不同輸入段落。
- P2：整句維持組字、移動游標、回頭改選詞、上下文語言模型。
- P2：新增邊說邊顯示的串流語音體驗。

第一版的「免切換混合」表示同一個字碼可由兩種方法解讀，選字後接著輸入；不等於已能把任意嘸蝦米碼與拼音串成一長串後完美自動切分。若要將後者提前列入必要範圍，需重估組字器工作量。

## 3. 系統分工與模組邊界

```text
HybridKeyboardPanel：按鍵、原始字碼、候選 UI
  └─ HybridInputRepository：查詢協調、快取、詞庫版本
      ├─ BoshiamyLookup：完整碼、前綴、碼表順序
      ├─ PinyinDecodeCore：合法音節、首字母、多路分段
      ├─ LexiconLookup：Room 批次查詞、常用詞索引
      ├─ CandidateRanker：來源分組、排序、去重
      └─ PersonalLearning：文字＋讀音鏈的使用偏好

AudioRecorder → RecordingController → 現有 Groq STT → 結果預覽

候選選字／語音結果 → InputCommitCoordinator → Android InputConnection
```

`PinyinDecodeCore` 為純 Kotlin：不依賴 Android UI、Room、網路或麥克風。Room 負責持久資料；解析器負責合法切分；UI 負責顯示與互動。這樣才能分別量測拆碼、查詞與畫面更新的成本。

建議新增檔案名稱為規劃名稱，實作時依現有 package 慣例微調：

| 模組 | 職責 |
|---|---|
| `PinyinNormalizer` | 大小寫、ü/v/u:、音節分隔符、詞庫聲調資料解析 |
| `PinyinSyllableTrie` | 記憶體中的合法音節與可延伸前綴 |
| `PinyinSegmentor` | bounded DP / beam，保留多種合法切分 |
| `HybridDecodeEngine` | 協調嘸蝦米、拼音與詞庫 lookup |
| `CandidateRanker` | 可解釋的來源優先級、頻率與學習排序 |
| `HybridLearningRepository` | 持久化合成候選與個人偏好 |
| `InputCommitCoordinator` | 字碼選取與語音插入的工作階段管理 |

## 4. 核心行為規格

### 4.1 字碼與拼音解析

- 保存 `rawInput`，不要在最前面刪掉分隔符、数字或所有非字母字元。
- 嘸蝦米依 CIN 實際合法鍵集合處理；不能預設所有碼表只用 a–z。
- 拼音建立 canonical syllables；UI 的選字数字與詞庫的聲調数字分開解析。
- 字庫匯入接受有分隔及帶調資料；無聲調查詢可匹配多個帶調讀音。
- `xi'an` 強制 `xi|an`；`xian` 保留 `xian` 與 `xi|an` 的合法路徑。
- 輸入中的尾端片段可作前綴搜尋；不可把尚未完成的尾音節當成已確認讀音來學習。
- 首字母代表一個音節的縮寫，與完整音節共同產生候選路徑；對每條路徑保留輸入範圍與匹配種類。
- 不以「一個中文字必等於一個讀音」硬性處理所有混合詞；多音字、英文與標點需保留詞庫的明確對應。
- 查不到時保留原始字碼供繼續修改；不因空白鍵在查詢完成前按下，就靜默把英文字母提交。

### 4.2 查詞、排序與候選可見性

候選依分數合併，而非把來源硬切成互不競爭的區塊。第一版分數規則為：

1. 精確全拼、精確首字母詞與嘸蝦米完整碼並列比較；全拼詞、首字母詞有可追溯詞頻時可勝出。
2. 使用者選字次數與最近使用時間調整順位；嘸蝦米同分候選保持 CIN 順序。
3. 精確分段組句與全拼／首字母混合候選。
4. 拼音未完成前綴與嘸蝦米前綴補全。
5. 有限模糊匹配，僅作備援；已有完整音碼命中時跳過昂貴模糊拆分。

上述是 Android 產品的初始規則，不宣稱與 MixType 的拆碼、語言模型或排序完全相同。Phase 0 以實際碼表與使用者語料固定具體預期。

- 各來源先取得足夠候選再合併；避免單一來源先占滿查詢上限。
- 完整嘸蝦米很多時，拼音候選仍應能透過展開／來源篩選找到，不可因總列表截斷而消失。
- 同顯示文字可合併為一列，但內部保存不同來源與讀音。讀音有歧義時，只學習已確認的路徑。
- 個人偏好不能讓模糊候選越過精確命中，也不預設改變使用者熟悉的嘸蝦米同碼順序。
- 常用度使用合法可散布、可追溯的詞頻來源；缺乏真實頻率時清楚標記為人工初始權重。
- 候選重新排序時保持穩定識別，選字綁定 candidate ID 與 query generation，避免快速更新造成點到另一筆。

### 4.3 合成詞與個人學習

候選至少攜帶：顯示文字、實際讀音鏈、來源集合、匹配種類、消耗輸入範圍、排序依據、穩定識別。資料庫 ID 為可選欄位。

- 個人拼音詞以「文字＋canonical reading chain」識別，不以臨時候選 ID 識別。
- 選取合成候選後 upsert 待學習紀錄，累積次數與最近使用時間；預設達三次有效確認，才提升為長期個人詞條。
- 首字母輸入碼不能冒充實際讀音；真正讀音取自命中的詞條。
- 嘸蝦米選字沒有已確認讀音時，只記錄嘸蝦米偏好，不猜拼音。
- 語音通常只回傳文字，不自動把它轉成拼音詞條或嘸蝦米碼。
- 保留清除／停用學習能力；密碼欄位與禁止學習的輸入情境不收集內容。

#### 三次學習與單字前移的明確規格

本規格依 2026-09-26 讀取的 MixType 實作訂定：詞語 `mixTypeAutoPromotionThreshold` 預設為 3；單字 `SingleCharacterPreferenceStore.rankingThreshold` 為 3。原始參考為 `InputHandler_MixTypeLearning.swift`、`lxSingleCharacterPreference.swift` 與 `UserDef.swift`。

| 對象 | 第一次／第二次 | 第三次及以後 |
|---|---|---|
| 詞語或已確認讀音的合成候選 | 保存待學習計數，尚未提升為長期個人詞 | 在讀音有效性檢查通過後加入個人詞庫，支援全拼、首字母及混合查詢 |
| 拼音單字 | 保存選取次數，維持原本單字順序 | 在同一無聲調讀音範圍內，依有效選取次數、最近選取時間向前排 |
| 嘸蝦米同碼候選 | 保留原 CIN 順序 | 預設仍保留原順序；若另加自適應排序，須作獨立設定與驗收 |

- 三次指實際確認選字／提交，不是輸入字碼三次或看見候選三次；不要求連續使用，也不因重啟歸零。
- 每個選字／提交事件具有唯一識別，同一操作只計一次；預覽、高亮、取消、失敗提交和重複回呼不計。
- 單字偏好以「無聲調讀音＋字」分組；多音字在不同讀音下分開計數。
- 單字只重排可比較的單字候選位置，不把長詞擠掉，也不越過完整嘸蝦米碼的來源優先級。
- 達三次不代表固定永遠第一；同組其他字也可能因更多選取次數排在前面，次數相同再比較最近使用時間。
- 個人詞條記住實際讀音鏈，三次門檻不會替未知讀音或不支援的字音配對背書。
- P0 學習使用者明確選取的詞與合成候選。P2 的整句組字提交學習需另立計數，不能與同一次明確選字重複累加；MixType 本身也分開保存這兩種觀察。
- 待學習計數、已學詞條與單字偏好均持久保存；清除單筆學習後恢复該筆的原始排序基準。

#### 手動新增個人詞典介面（P0）

現有 `ime/hybrid/HybridDictionaryActivity.kt` 已有「新增個人詞」、拼音輸入及「加入個人詞並建立首字母縮寫」的基礎介面，透過 `HybridInputRepository.addPersonalPhrase()` 存入 PERSONAL 詞條。本次沿用並完善此入口；目前僅確認程式碼，尚未確認 S26 安裝版本具有相同行為。

入口：鍵盤的詞庫入口／設定 → 個人詞典。介面提供：

- 詞語欄，例如「耀文」。
- 分音節拼音欄，例如 `yao wen`；清楚提示各音節以空白分隔。
- 即時顯示自動產生的完整拼音 `yaowen` 與首字母 `yw`，不需要另填縮寫。
- 儲存、個人詞列表、依文字或拼音搜尋、修改读音、刪除單筆。
- 區分手動新增與自動學習來源；清除自動學習不應一併刪除手動詞條。

儲存與匹配規則：

1. 手動新增表示使用者已確認，直接建立長期個人詞條，繞過三次自動學習門檻。
2. 保留使用者確認的讀音；若提供字庫推導讀音，必須可修改，尤其人名與多音字不可靜默猜定。
3. 檢查空白、合法音節與讀音對應。新姓名不需先存在於整詞字庫才能新增；遇到既有字庫未知的讀音配對，提示確認，不能沿用自動學習的整詞門檻一律拒絕。
4. 同文字同讀音避免重複新增；同文字不同讀音可分別保存。
5. 儲存完成後更新詞庫版本與候選快取，回鍵盤立即生效，不需重啟 app 或鍵盤。
6. `yw` 精確命中「耀文」的首字母；`yaowen` 及支援的混合拼音如 `yaow` 也可查得。它在相同拼音匹配組中享有手動個人詞優先級，不保證越過完整嘸蝦米碼或永遠固定第一。
7. 個人精確縮寫有獨立檢索額度，不可在通用詞庫查詢截斷時被漏掉；若候選很多，能由展開／來源篩選完整取用。
8. 這是鍵盤打字詞典。既有語音專有名詞提示不自動等於拼音詞條；是否將手動詞語文字同步提供給語音提示，列為獨立可選設定。

### 4.4 Groq 與打字的交接

第一版採錄音停止後轉錄，預設沿用既有 Groq 模型設定；模型選擇與繁體中文輸出品質用固定語料比較，不預設較快模型也一定較準。

操作順序：按麥克風 → 錄音 → 停止 → 辨識中 → 顯示文字 → 點選插入。

- 有未選字碼時不啟動錄音，明確提示先完成或清除組字；避免語音先插入、舊組字稍後才提交造成順序錯亂。
- 錄音／處理中暫停一般組字輸入；使用者可取消語音並恢復原字碼。
- 既有組字未完成且語音已辨識成功時，保留兩份內容。先讓使用者完成或清除舊字碼，再插入語音，避免改變文字先後順序。
- 錄音開始記錄 editor session token 與選取位置版本；session／游標選取變更後禁止自動插入舊結果。
- 同一 app 的不同欄位也要視為可能不同 session；只比 package name 不足。
- `onStartInput`、`onFinishInput`、InputConnection 失效、同欄位游標／選取變更都納入有效性判定；無法確認時保留預覽供重新選擇插入。
- 每次插入有唯一操作 ID，成功後消費結果；連點、重複回呼、重試不得重複輸入。
- 取消或失效的請求，即使較晚回傳也不能重新顯示／提交成有效結果。
- 無網路、Key 錯誤、429、timeout、空辨識、靜音及權限拒絕均需有明確可恢復狀態。
- 語音原文預設可直接插入，AI 潤飾／翻譯是選用後處理，不阻塞基本轉錄路徑。
- 既有「送出」等語音指令不得在新流程中繞過預覽直接發送；檢查並提供明確的語音指令啟用設定。
- 繁體提示不等於保證繁體；測量實際輸出，必要時另設可選繁簡轉換，保留原文供核對。

## 7. 效能設計與量測

先記錄基準，再比較新引擎。不能用 cache 命中或只跑單元測試宣稱 S26 已順暢。

- 音節 trie 常駐小型記憶體索引；大型詞庫維持持久儲存，避免未量測就整庫載入。
- DP 過程先產生可批次查詢的 segment 集合，合併重複詞庫查詢。
- dispatcher 分工：UI 主執行緒只顯示；拆碼運算與資料讀取在適當背景執行。
- 每個查詢帶 generation ID，合作式檢查取消；過時結果不得更新候選列。
- 快取鍵包含字碼、解析設定、詞庫版本與個人詞版本；新增詞、匯入、學習後失效。
- 初始演算法上限提案：beam 16–32、每段詞候選最多 24、每次 UI 回傳 12；可展開來源查詢，不能把 UI 首頁上限當成全詞庫上限。
- 超長字碼採分段或明確提示上限；不得靜默截斷字碼或產生錯誤已消耗範圍。

以下是待真機驗證的開發目標，並非目前測得結果：

| 指標 | 初始目標與測法 |
|---|---|
| 常見 1–12 字元輸入 | 從按鍵到對應候選完成繪製，P95 ≤100ms |
| 較長組合輸入 | 13–30 字元語料，P95 ≤200ms，鍵盤持續可回應 |
| 每個新前綴首次查詢 | 單獨計算 P50/P95/最慢值，不與相同 query cache 命中混合 |
| 冷啟動 | 獨立記錄鍵盤首次出現及首次查詞耗時；以階段 0 基準設定門檻 |
| 資料庫成本 | 每次字碼查詢記錄 SQL 次數與耗時；避免隨路徑數暴增 |
| Groq 語音 | 分錄音停止、編碼、上傳、API、预覽各段計時；依音長與網路分組，階段 0 再訂門檻 |
| 記憶體／長時間使用 | 記錄新引擎增量記憶體、峰值、連續輸入與開關鍵盤後是否持續增長 |

每組核心語料至少量測 100 次，區分冷／暖啟動、網路條件及裝置設定。除錯紀錄只包含匿名識別、耗時與計數，不記錄 API Key、完整個人詞或錄音內容。

## 8. 驗收語料與情境

語料使用獨立小型 fixture 測演算法，另用合法完整詞庫及使用者 CIN 做品質驗收。不同詞庫的候選文字可能不同，不能把字庫缺詞誤判為拆碼錯誤。

| 類型 | 案例 | 預期 |
|---|---|---|
| 嘸蝦米 | 從實際 CIN 選完整碼、同碼多字、簡碼、前綴 | 精確結果與來源碼表相符、順序穩定 |
| 來源碰撞 | `wbzd` 同時命中嘸蝦米完整碼與拼音首字母詞 | 「我不知道」在本地初始詞頻加權後排前，嘸蝦米候選仍保留 |
| 快速空白鍵 | 最後字母後、候選列仍顯示載入中即按空白 | 等本次輸入的查詢；有候選選第一個，無候選保留組字，不提交英文字母 |
| 全拼 | `nihao` | fixture 有「你好」時可找到 |
| 首字母 | `nh`、單字母 `s` | 可查多字詞並依常用度排序 |
| 拼音混合 | `nhao`、`nihaoma`、`nhm` | 合法完整／縮寫路徑可查相應詞 |
| 分隔與歧義 | `xian`、`xi'an`、`fangan` | 保留合法多路；明確分隔會限制切分 |
| 特殊拼音 | 大小寫、ü/v/u:、詞庫帶調資料 | 正規化一致，不破壞原字碼 |
| 組句 | `guolaiyixia`，fixture 只提供可組合詞段 | 即使無完整詞條仍能有限組合 |
| 合成學習 | 選取新組句、重啟後再輸入 | 偏好可持久保留，讀音不被誤記 |
| 三次詞語學習 | 同文字與讀音確認 1、2、3 次，中途重啟 | 前兩次為待學習，第三次提升；重啟不丟計數 |
| 單字前移 | `yao` 明確選「耀」三次，並設其他同音單字 fixture | 前兩次維持原順序；第三次在單字位置向前排，不跨越嘸蝦米精確組 |
| 學習去重 | 候選預覽、取消、同一提交重複回呼、提交失敗 | 均不增加有效選取次數 |
| 手動個人詞 | 介面新增「耀文／yao wen」，立即輸入 `yw`、`yaowen`、`yaow` | 可找到「耀文」，不需先選取三次；有來源碰撞也可展開找到 |
| 個人詞管理 | 重啟、修改讀音、刪除、重複新增、多音字、清除自動學習 | 儲存持久有效；修改／刪除即時生效；手動詞不被清除自動學習誤刪 |
| 偏好管理 | 清除單筆學習、停用學習、多音字不同讀音 | 清除後恢復基準，不串讀音或誤累加 |
| 模糊，P1 | `jtqqhh` 等明確定義一編輯語料 | 僅在 fallback 啟用，精確結果不被壓過 |
| 快速操作 | 快打、連刪、候選更新時點選 | 無過期候選覆蓋或錯字提交 |
| 語音中文 | 繁中常用句、商品名、人名、數字及中英混合 | 原文可核對，專名錯誤可修正 |
| 切換輸入 | 未選完字碼開始錄音，取消／成功各一路 | 原字碼可恢復，先後順序清楚 |
| 切換欄位 | 同 app 换欄、换 app、游標移動、收起鍵盤 | 舊結果不自動插入新位置 |
| 重複與中斷 | 連點插入、斷網、429、取消後晚回傳 | 不重複輸入、錯誤可恢復 |
| 升級 | 既有詞庫、使用紀錄、剪貼簿及錄音歷史 | migration 後數量／內容一致 |

真機至少涵蓋 Samsung Notes、LINE、Chrome 表單，以及使用者常用工作 app；每個 app 涵蓋單行、多行、選取文字與刪除。另確認密碼／数字欄位、橫直向、螢幕鎖定、麥克風權限、錄音中切 app 與程序被回收。送出動作在測試草稿或自用環境驗證。

## 10. 資料保留、回退與引用方式

- 目前兩個專案都有持續開發；開始實作先記錄相關差異，不對 dirty tree 做 reset，也不從只有 HEAD 的新工作樹遺漏現有必要修改。
